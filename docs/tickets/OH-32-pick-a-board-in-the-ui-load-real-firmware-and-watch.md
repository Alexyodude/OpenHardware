The headline: a person opens the emulator, chooses a development board, points at firmware they built, and the board runs it. Every piece exists separately and none of them meet.

What exists. OH-19 landed target selection driven by which cores are built, and refuses anything not ready rather than accepting-and-disabling. OH-10 landed the format layer (UF2/ELF/HEX/bin -> Image) and artefact discovery over PlatformIO and arduino-cli builds. tests/cortexm0/test_blink.py runs a real compiled image on the RP2040. OH-22 is building the catalogue view.

What is missing is the seam: a load_firmware operation in webui/api.py that takes a board rather than a core, resolves that board to its runtime description, checks the image belongs on that chip, and starts it. Today the emulator is chosen by *core*; a person thinks in boards.

Refuse loudly at the joins, since each is a different failure. A board with no runtime description cannot run anything -- 25 of 26 are in that state. A core that is not built cannot run its boards. And an image built for the wrong chip must be rejected on its own headers, not run until it faults.

Done when a PlatformIO artefact, unmodified, is selected against a board in the UI and executes -- RP2040 first, since it is the only board that can prove it.

Depends on OH-10 (the load path), OH-19 (selection), OH-22 (the catalogue), and the runtime board contract ticket. It claims none of their files; the seam is webui/api.py, which is the layer both transports share.

**Note 2026-08-25:** Seam built and proven for RP2040. webui/api.py gains load_firmware(board, data, base=None, vector_table=None) -> BoardSession: board name in, a core installed with that board's memory map and stopped at its reset vector out. It calls catalogue.py (which chip, which core), targets.require_selectable (is that core built), webui/boards/<chip>.py install() (the map), firmware.load_image (bytes -> Image) and core.<core>.abi.Cpu; it reimplements none of them. Evidence, all on XIAO-RP2040-DIP with the committed 76-byte arm-none-eabi-gcc blink.bin, unmodified: bare .bin at 0x10000100, the same image behind 256 bytes of boot2 filler at 0x10000000, and a hand-packed ELF needing no base all reach vt=0x10000100 sp=0x20042000 pc=0x10000108 and produce 45 pin transitions at a 453-instruction period, matching what tests/cortexm0/test_blink.py measured. tests/webui/test_board_run.py: 19 passed. check_layering, check_board_claims and check_licenses OK. NOT DONE: the UI half. webui/emulator_server.py and webui/static/** are another ticket's, so nothing in a browser calls this yet; BoardSession.as_json() is the shape a transport would return and it is the only work left for the headline. Also not done: artefact discovery is NOT inside api.py, deliberately - tools/import_firmware already owns it and api.py taking bytes keeps webui/ from importing tools/. CONTRADICTIONS. (1) The ticket says 25 of 26 boards lack a runtime description; measured today it is 24 of 26, and riscv32 was built by another session mid-ticket, so seven ESP32-C3/C5/C6 boards are now in the state of having a built core and no description - a combination the ticket treats as hypothetical and which is now the commonest refusal. (2) I put the core refusal BEFORE the description refusal, opposite to the ticket's ordering: a memory map for a chip nothing executes buys nothing, and catalogue.missing_cores already orders the backlog by core. (3) Real defect in a neighbouring module, not fixed because webui/firmware.py belongs to OH-10: parse_uf2 returns an Image with ZERO SEGMENTS rather than raising when the requested family is absent from the file. An ESP32-C3 UF2 asked for as RP2040 parses 'successfully' into nothing - load nothing, report success, which is the exact failure this ticket exists to stop. Caught at the seam (test_a_uf2_for_another_family_is_refused_rather_than_loaded_empty) but the honest fix is in parse_uf2. (4) The vector table cannot be derived from an image alone on RP2040: bare-metal images link past boot2 and pico-sdk images include it, so both 0x10000000 and 0x10000100 are ordinary. Both candidates are tried and each is CHECKED against the board's own map (sp must have mapped memory below it, reset must be Thumb and in an executable region) rather than assumed - this is what rejects 0x4b32b500, two instructions of boot2, as a stack pointer. (5) Architectural: webui/api.py is the rcontrol/PICSimLab command surface and an in-process core session is a different backend entirely; built there as the ticket directs, delimited by a section header saying it shares the file and nothing else, and named as the part to move when a third backend arrives. Unrelated pre-existing failures seen while working: tests/webui/test_targets.py and test_board_catalogue.py both pin the core list and fail on riscv32 having landed.

**Note 2026-08-25:** Transport half landed. webui/emulator_server.py gains three routes: POST /api/board/load (board name + base64 artefact -> as_json), POST /api/board/run ({steps} -> {steps,status,detail}), GET /api/board/state (registers, a memory window, and watched peripheral words). Behaviour stays in webui/api.py and the server is a translation, the same split CLAUDE.md records for emulator.py. EACH REFUSAL REACHES THE CALLER AS ITSELF: BoardRunError now carries a stable reason slug from api.REASONS and BOARD_ERROR_STATUS maps it to a status - 404 unknown-board, 409 core-not-built and chip-not-described (only a build or a new file fixes those), 400 for nothing-for-this-chip, outside-the-board-map, no-vector-table, budget-refused, window-refused, window-outside-the-map, plus unreadable-artefact for firmware.FirmwareError. Verified against a real server on 127.0.0.1:8099 outside pytest: load 200, run 200, state 200 with pc advanced and SIO GPIO_OUT/GPIO_OE both 0x02000000 (GP25 driven and an output); bad Origin 403; unknown board 404; RP2350 409; ESP32-C3 409; wrong addresses 400 outside-the-board-map; no base 400 unreadable-artefact. tests/webui/test_board_run.py 38 passed; whole tests/webui 306 passed 1 failed 17 skipped, the failure being test_targets.py pinning build_core.cores() to two cores and riscv32 having landed - not mine. check_board_claims, check_layering, check_licenses, check_banned_symbols all OK. SECURITY: loopback bind and Origin check untouched and both tested on the upload route specifically. Added two ceilings because this is the one route that takes a file - MAX_IMAGE_BYTES 8 MiB (sized from the 4 MiB largest flash in the catalogue) and MAX_BODY_BYTES 16 MiB checked from Content-Length BEFORE any allocation, which previously was unbounded for every route. base64 decoded with validate=True so rubbish is refused rather than silently truncated into a short file. FINDING, in the core rather than in my code: cpu.read_block covers regions only and cpu.in_range is false for a mapped register by design, so a naive state() window over SIO faults. Memory and peripherals are therefore separate arguments - at/len is a window over regions, words= reads mapped registers one at a time with read_word - and pointing at/len at a peripheral is refused with a message naming words=. Without that split the state view could not show GPIO_OUT, which is the only thing worth watching on a blink. STILL NOT DONE: webui/static/emulator.{js,html}, claimed by OH-39. The wire shape for all three routes is written into the emulator_server module docstring so the browser side is a fetch call and a file input; nothing else is left.
