Of 582 pads across 26 boards, 28 carry a simulator pin index and all 28 are on Arduino Uno. Every XIAO file states the consequence in its own 'assumption' field: 'A pad with pin null draws and refuses a wire.' This is the largest single gap between the board data that exists and a board you can run code on -- geometry without a pin index is a picture with coordinates.

The mapping from a silkscreen label to an MCU pin is published, just not in the CAD. It lives in board-support packages: an Arduino core's variant.cpp and pins_arduino.h, a Zephyr board .dts, CircuitPython's board module. Extract label -> chip GPIO from those, per board, with the source file named in the output the way 'derivation' already names the footprint.

Three things that will bite. The label is not the GPIO -- XIAO 'D6' is GPIO21 on ESP32-C3 and a different number on RP2040, so the mapping is per board and never per family. A board may appear in several board-support packages that disagree; a disagreement gets recorded, not averaged. And a pad that no board-support package covers stays null, because the current null is honest and a guessed number would wire the circuit wrongly while reporting success.

Done when a XIAO pad accepts a wire, every non-null pin traces to a named vendor file, and the count of resolved pads is generated rather than written down.

Note: writes into webui/boards/*.json, which OH-22 claims wholesale.

**Note 2026-08-25:** Extractor built and verified against real fetched vendor sources; network was available, no fixture stand-in. tools/import_pindefs.py reads six board-support packages fetched blobless+sparse into third_party/bsp/ (git-ignored): zephyr 0a2e408 boards/seeed/<board>/seeed_xiao_connector.dtsi, arduino-pico 33201a6 and arduino-esp32 2787dab variants/<v>/pins_arduino.h, seeed-nrf52 667f05f and seeed-samd 2e6b174 variants/<v>/variant.{h,cpp}, silabs-arduino 6128e93 variants/xiao_mg24/{pins_arduino.h,arduino_variant.cpp}. Result, generated by --summary and not written down: 321 of 550 XIAO pads resolve, 229 stay null, 0 disputed; every resolved pad names the file and revision that resolved it (audited: zero resolved pads with an empty sources list). Trap 1, per-board not per-family: confirmed, D6 is GPIO0 on RP2040 and GPIO21 on ESP32-C3, and the registry is keyed per board. A worse trap the ticket did not name also arose: on the nRF52840, SAMD21 and MG24 Arduino cores D6=6 is an index into the core's own pin table (g_ADigitalPinMap/g_APinDescription/gPinNames), not a GPIO, so a uniform pins_arduino.h reader emits D0..D10 as 0..10 for three families and looks successful; hence two readers and a per-board choice. Trap 2, disagreement: mechanism built and fixture-tested, but measured zero disagreements across all 25 boards at these revisions. Trap 3, uncovered pads stay null: 229 do, each with a reason; GND, VBUS, 3V3_OUT, EN, PAD, MTMS, SWD and SAMD11_* are not GPIOs of this chip. Deliberately not done: webui/boards/*.json, claimed by OH-22; the report carries the footprint pad number so the join is on that, not on label order. Blocker for OH-22: 123 resolved pads on 8 boards (SAMD21, MG24, nRF54L15, nRF54LM20A) name a chip pin with no flat integer index (PA02, PC0, P2.08) because those vendors publish no flat GPIO numbering, so index is null and chip_pin is the answer; what the simulator's integer pin means there is undecided. Also noticed: webui/boards/XIAO-XIAO STM32C5-SMD.json has a doubled name prefix, likely an OH-25 import bug, and that board has no board-support package anywhere (0 of 35 pads).
