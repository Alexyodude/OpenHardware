Found by OH-200's review (2026-10-08). A board file's `pindefs.derivation` and `assumption` say where its `chip_pin` values came from, and on eight XIAO board files they say something false.

`BOARD_DERIVATION` in `tools/import_pindefs.py` says the file was generated "from the board-support packages in `packages`", that "Nothing was inferred from the CAD", and that a label resolves only when every package covering the board names the same pin. `assumption_for` says `chip_pin` was "read out of the board-support packages named in `pindefs`". Both are written onto every board a board-support package covers.

Some of those boards also read the vendor's own board CAD, `seeed-pcb`, for pads no package names: the MG24, nRF54L15 and nRF54LM20A XIAOs (DIP and SMD) before OH-200, and since OH-200 the XIAO ESP32-C5-SMD and C6-SMD, whose MTMS, MTDI, MTDO, MTCK and BOOT come from Seeed's board file alone. On those files the derivation and the assumption contradict the pads they describe, and contradict the HEADER block OH-200 generates for the same pads, which says that source "is not a board-support package".

`BOARD_DERIVATION_UNCOVERED` and `MANIFEST_DERIVATION` already describe a CAD source truthfully. Give a covered board that also reads a non-firmware source a derivation and an assumption that name what the CAD answered, generated rather than typed, and regenerate the board files. A covered board that reads only packages keeps today's sentence.

While in `header_table`, two readability edges from OH-200's confirm review: the local set called `cad_rows` means "any CAD source named the row" while the `HeaderTable.cad_rows` field it filters into means "only the CAD named it" (rename the locals, e.g. `cad_named` / `package_named`); and the F3 test's docstring does not say that its fake `D6/MTDI` pad is what exercises the `alternatives` keying, so a later simplification could remove it unnoticed.

Done when no board file says its pins came only from board-support packages while a pad on it rests on the vendor's CAD, a test fails if one does, and the generated files regenerate byte for byte.

**Note 2026-10-08:** In review. No board file now says its pins came from board-support packages alone while one of its pins rests on Seeed's board CAD. A test fails if one does, and the files regenerate byte for byte.

FOUND BY COMPUTATION. A pad rests on a source that is not firmware where its `chip_pin` is resolved and one of the claims `board_report` cites comes from a package with `firmware=False`; a citation's first word is its package, as `header_table` reads it. Six covered XIAO files have such a pad: XIAO-ESP32-C5-SMD and XIAO-ESP32-C6-SMD (MTDI, MTDO, MTMS, MTCK, BOOT), XIAO-MG24-SMD (SWDIO, SWCLK, traced), XIAO-nRF54LM20A-DIP and XIAO-nRF54LM20A-SMD (NFC2, NFC1), and XIAO-nRF54l15-SMD (NFC2, NFC1). The ticket's MG24 and nRF54L15 DIPs are not among them. Like the C5 and C6 DIPs, they list `seeed-pcb` in `packages` and none of their pads rests on it, so they keep today's sentences. Neither is XIAO-RP2350-SMD, which reads zephyr and arduino-pico alone and so keeps today's sentences, as the ticket says. The uncovered STM32C5 and the manifest boards already had sentences of their own and are unchanged.

WRITTEN. `board_derivation_with_cad` in `tools/import_pindefs.py` writes the derivation, and `assumption_for` takes `cad` and `answered`. `filled_board` fills all of it from the report's claims, and no label or package is typed into the code. On XIAO-ESP32-C5-SMD the derivation reads: "Generated by tools/import_pindefs.py from the sources in `packages`, at those revisions, and not every one of them is a board-support package. The vendor's own CAD among them, `seeed-pcb`, answered `MTDI`, `MTDO`, `MTMS`, `MTCK`, `BOOT`; the board-support packages, `arduino-esp32`, `zephyr`, answered every other pad that resolves. Nothing was inferred from the silkscreen or a pinout image: a label resolves only when every source in `packages` that defines it names the same pin, and `python tools/import_pindefs.py <board>` prints the file that named it." Its assumption's clause reads: "`chip_pin` and `chip_index` are what tools/import_pindefs.py read out of the sources named in `pindefs`: the vendor's own CAD, `seeed-pcb`, for `MTDI`, `MTDO`, `MTMS`, `MTCK`, `BOOT`, and the board-support packages for the rest; a pad whose `chip_pin` is null says why in `why_null`." Where a single package answered the rest, as on the Nordic boards with Zephyr alone, the noun is singular: "the board-support package, `zephyr`,".

REGENERATED. `--write-boards` wrote exactly those six files and changed only their `assumption` and `pindefs.derivation`. Every other board file was unchanged, the manifest boards included. `--write-headers` left all five modules unchanged.

TEST. `test_no_board_file_says_its_pins_came_from_packages_alone_while_one_rests_on_cad` computes the pads that rest on CAD from `board_report` itself. Any file with such a pad must not say "from the board-support packages in `packages`", "Nothing was inferred from the CAD" or "read out of the board-support packages named in `pindefs`". A covered XIAO file must also name each of those pads in both sentences, and a covered XIAO file without one must keep `BOARD_DERIVATION` exactly. The test also asserts that the three phrases are still in the sentences they quote. It went red on the committed files before regeneration: "('XIAO-ESP32-C5-SMD', ['MTDI', 'MTDO', 'MTMS', 'MTCK', 'BOOT'], [all three phrases])". DELIBERATE BREAKS after the fix, both red and both restored by `git checkout`: (A) XIAO-nRF54LM20A-DIP's derivation put back to `BOARD_DERIVATION` gave "('XIAO-nRF54LM20A-DIP', ['NFC2', 'NFC1'], ['from the board-support packages in `packages`', 'Nothing was inferred from the CAD'])"; (B) XIAO-RP2350-SMD's derivation given the CAD shape failed the half that says a packages-only board keeps the sentence.

ALSO. `header_table`'s locals are now `cad_named` and `package_named`, and behaviour is unchanged. The F3 test's docstring now says that its `D6/MTDI` pad exercises the `alternatives` keying. Measured: keying a pad by its whole label alone turns that test red with `{'D6': ('FAKE-DIP',), 'D10': ('FAKE-SMD',)}`.
