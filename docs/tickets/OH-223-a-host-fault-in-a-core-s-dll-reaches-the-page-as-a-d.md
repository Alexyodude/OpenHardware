Found by OH-222's review (2026-10-10), by running it. When a core's DLL faults on the host -- a divide error, an access violation -- ctypes on Windows catches the structured exception around the foreign call and raises `OSError` out of `Cpu.step()`. Nothing above it expects that:

- `webui/emulator.py`'s `Session.step` (~153-158) catches only `abi.Unimplemented`;
- `webui/emulator_server.py`'s `Handler._api` (~886-899) catches BoardRunError, FirmwareError and (ApiError, EmulatorError, ValueError), not OSError.

So the request gets no reply (RemoteDisconnected, a traceback on the server's stderr), and the machine is left half-executed: the core had already advanced IP past the instruction when it faulted, so the next step runs the instruction after it, status still "running". Shown with OH-222's IDIV against the unguarded DLL: the IDIV was silently skipped and the following HLT ran. OH-222 removed that one fault; this ticket is for the next one, whatever it is.

A fault in the core is the core's bug, and the page should say so and stop, not carry on from a state no instruction produced (rule 9: handle it at the boundary where it entered, with the values that caused it).

STEPS:
1. In each core's `abi.Cpu.step` (i8086 first; check avr, cortexm0, riscv32 for the same shape), turn an `OSError` from the foreign call into an `AbiError` subclass that names the core, CS:IP or PC, and the opcode bytes at it, chained from the OSError.
2. In `Session.step` (and the board session's run loop, if it has its own), set status to a terminal "faulted" with that detail and stop stepping; the page shows it the way it shows other stops.
3. A test that provokes a host fault deterministically without a real core bug -- e.g. a test-only export, or a stub library -- and asserts the status and the message, seen to fail first.
4. Say what happens on Linux, where the same fault is a signal ctypes does not catch and the process ends; whether anything should be done there (a subprocess per session is a larger design) is a decision to record, not to make silently.

**Note 2026-10-12:** FIXED at 446514b (i8086, session, page) and 4671fe1 (avr); claims at abb042b. Steps 1-4 done for the files this ticket may hold; cortexm0, riscv32 and webui/api.py are left to their owners, below.

MECHANISM. core/i8086/abi.py: HostFault(AbiError). Cpu.step reads the registers into a buffer the Cpu keeps, then calls i8086_step inside try/except OSError and raises HostFault from it. The message names the core, the CS:IP where the instruction began, the six bytes there as the processor fetches them (wrapping inside CS), the CS:IP the core left, and the OSError's text, e.g. "i8086: the core faulted on the host (exception: integer overflow) executing the instruction at 0000:0509; the bytes there are F7 FB F4 00 00 00, and it left CS:IP at 0000:050B. That is a bug in core/i8086, not in the program, ...". If reading the machine back faults as well, the message says so instead of a second OSError replacing the HostFault. webui/emulator.py: Session.step turns HostFault into a terminal status "faulted" with the message as detail, not counted as a step; run stops on it; reset and load clear it as they clear halted. The i8086 binding has no other foreign call that executes instructions (run is Session.run's Python loop over step). The server needed no change: /api/step and /api/run answer 200 {steps, status: faulted, detail}, as an unimplemented opcode does. emulator_server.py's error mapping is untouched, so a ValueError from OH-161's coming /api/board/drive still reaches the (ApiError, EmulatorError, ValueError) clause as a 400; giving it a REASONS slug is that route's. The page: emulator.js renderStatus writes any status into #status (text and data-state) and #detail and disables Step and Run when it is not running, and runContinuously stops on it, so it needed nothing; emulator.css styles faulted as it styles unimplemented. Not opened in a browser.

COST, measured here (Python 3.14, Windows): reading the registers before each step takes Cpu.step from 0.22 to 0.42 us, and a 200,000-step Session.run of jmp $ from 0.114-0.119 s to 0.154-0.160 s (+35%). Accepted for the i8086: a debugger, runs bounded at MAX_RUN_STEPS, a conformance suite whose per-case setup dwarfs it; Cpu.step's docstring says so. Not for a board core: an AVR run loop measured 0.195 us a step, 0.36 with avr_pc read first, nearly halving instructions per second. So core/avr/abi.py's HostFault names where the core LEFT the PC, says the core advances the PC before executing, and shows the program words from PC-2 to PC. If the precise instruction is wanted on a board core, the core recording its own entry PC (a C export and an ABI bump) is the way, not a per-step read.

AVR. webui/api.py's BoardSession.run catches runtime.abi.AbiError, so an AVR host fault now stops a board run ("stopped", the message as detail) and the request is answered. Probed through a live server with tests/avr/blink/blink.bin on the Arduino Uno and avr_step faked on its 1000th call: POST /api/board/run 200, 999 steps, stopped; a second run 200, 0 steps.

TESTS. tests/webui/test_host_fault.py (5) and tests/avr/test_host_fault.py (2). The fault is faked and only the fault: i8086_step is replaced (monkeypatch on the loaded CDLL) by a function that gives every instruction to the real core except IDIV r/m16, where it does what OH-222's review saw the unguarded core do -- IP moved past the instruction, nothing else written -- and raises OSError("exception: integer overflow"), the text ctypes raises for STATUS_INTEGER_OVERFLOW. The program is OH-222's probe, BA0080 B80000 BBFFFF F7FB F4. Everything above the foreign call is real: Cpu.step, Session, handle_api, Handler._api and a server on a loopback socket. Asserted: HostFault, an AbiError, chained from the OSError, naming 0000:0509, F7 FB F4 and CS:IP left at 0000:050B; a read-back that faults too is said, not raised; Session.run gives (3, faulted) and state() agrees; step and run afterwards do nothing and the registers do not move; reset gives running and then the same fault at the same place; through the server, /api/run 200 faulted, /api/state 200 faulted with IP 050B, /api/step 200 with 0 steps. AVR: avr_step faked at word 2 of LDI, LDI, ADD, RJMP; asserted HostFault, AbiError, chained, "PC at word 0x0003", the words 0xe012 0x0f01 0xcfff, r16 untouched; and the read-back case.

LINUX, measured in a local container (node:24, Debian, Python 3.11.2, --network none): a ctypes call into a .so computing INT32_MIN / -1 exited 136, "Floating point exception (core dumped)", with no OSError; ctypes.string_at(16, 1) exited 139, "Segmentation fault". On this Windows machine the same string_at raises OSError "exception: access violation reading 0x0000000000000010" and the process goes on. So on Linux (and macOS, where the faults are the same signals) a host fault in any core ends emulator_server.py with every session in it, the page gets connection refused, and HostFault is never raised. The tests fake the fault and so pass on Linux too: right about the Python, silent about the signal. HostFault's docstrings in both bindings say Windows only.

DECISION, Linux: nothing is done in this ticket. Nothing in-process can recover: a Python signal handler runs between bytecodes after the C has returned, so a SIGFPE or SIGSEGV handler that returns re-executes the faulting instruction (the signal module's documentation says catching those makes little sense); a sigsetjmp/siglongjmp around each step would change every core, and jumping over C++ frames skips their destructors. What would work is a child process per session that owns the core, the parent reporting faulted and the signal when the child dies; that turns every Cpu call into IPC (a step is about 0.2 us here, a pipe round trip tens of us), so the run loops would have to move into the child. A design of its own and not filed here: whether hosting on Linux matters enough is the owner's call.

A fault in Decode would leave IP unmoved (ExecuteOne decodes first), so after the step reports faulted, /api/state's disassembly would decode the same bytes and fault again, dropping that request. M1. The per-step register read is gone. i8086_step now records the step's CS:IP in the ABI's Handle, two stores, and i8086_step_entry exports it as (cs << 16) | ip (I8086_ABI_VERSION 8 -> 9, in abi.h, abi.cc and abi.py). The binding reads it only after a fault. The AVR has the same arrangement: avr_step records its PC, avr_step_entry exports it (AVR_ABI_VERSION 3 -> 4), and its HostFault now names the word the step began at and the first two words there, not where the PC was left; the PC-2..PC heuristic is gone. load() refuses a library with another ABI version, so no fallback is needed. Timings, measured in one run on this machine against the same DLL: Cpu.step 0.228 us at 8d86171's shape, 0.418 with 4375a59's read before every step, 0.229 now; a 200,000-step Session.run of jmp $ 0.120 s, 0.159 s, 0.117 s. AVR run loop 0.19 us a step before, 0.20 now, the difference being the closed-handle check. This supersedes the COST paragraph above: nothing is read per step on either core.

M2. HostFault carries at (CS:IP of the instruction), code (the bytes read there) and left (CS:IP the core left), the AVR's the same in words. Session records fault_at from it, reset and load clear it, and Session.disassembly starts at it and marks that line current, so after a fault the listing's first line is the instruction that faulted, not the next. The registers, and so the page's #where, still show where IP was left, which is true; emulator.js is OH-221's and unchanged. The tests assert on the fields.

L5. core/avr/abi.py: a step after close() raises AbiError("this Cpu has been closed") before the foreign call. Before, it handed the core a null handle, which faulted for real (an access violation through ctypes) and was reported as a bug in core/avr.
L6. Cpu.decode raises HostFault from an OSError, naming where it was decoding, and says decoding changes nothing. Session.disassembly walks the listing itself rather than calling disasm.disassemble_range, which returns all its lines or none, so a decoder fault becomes the listing's last line with the lines before it kept, and /api/state answers; reading the state leaves the status alone.
L7. Each read back -- where the step began, the bytes there, the registers -- is its own try; bytes read before one faults are kept, and each failure is named in the message.
L8. The message says "the first 6 bytes there", since a prefixed 8086 instruction can be longer than FAULT_BYTES.
L9. When ctypes' text says "access violation writing", the message says the process may be damaged beyond the machine and to restart it, rather than reset (i8086) or reload (avr).
L10. webui/emulator_server.py released for OH-161 at 705ea5e.
