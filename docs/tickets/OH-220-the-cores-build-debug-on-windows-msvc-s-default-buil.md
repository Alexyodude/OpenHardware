Every core this repository builds on Windows is a Debug build: unoptimised, with runtime checks. `tools/build_core.py` configures with no build type and builds with `--config Release`, which a single-configuration generator (Ninja, which it prefers) ignores. `CMakeLists.txt` then means to default to Release:

    if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
      set(CMAKE_BUILD_TYPE Release CACHE STRING "" FORCE)
    endif()

but that runs after `project()`, and on MSVC CMake has already set CMAKE_BUILD_TYPE from its platform default, `CMAKE_BUILD_TYPE_INIT` = Debug, so the condition is false and the fallback never fires.

Seen 2026-10-09: `lane3`'s build/ was deleted and configured fresh by `python tools/build_core.py --clean` with CMAKE_BUILD_TYPE unset in the environment, and its CMakeCache.txt says `CMAKE_BUILD_TYPE:STRING=Debug`, `CMAKE_CXX_FLAGS_DEBUG:STRING=/Zi /Ob0 /Od /RTC1`. The main checkout's and every lane's cache say the same.

What it costs, measured by OH-161's reviews on this machine: `riscv32_step` through ctypes ran at 1.89M steps/s on build/'s Debug core against 6.83M on a Release core built outside the repo (OH-161 step 2's review); `session.run` on a QT Py C3 and a SparkFun C5 ran at 1.23M steps/s on the Debug core (OH-161's delay() review). Since delay() waits on the SYSTIMER (OH-161), a delay(500) on a 160 MHz ESP32 is 80,000,000 instructions, which at the Debug rate is about a minute of wall clock per half period of the page's default Blink. clock.js's own figures (2.6M steps/s for an Uno) were taken on whatever core was built then.

STEPS:
1. Make a configure that names no build type produce a Release build on every generator: set the default before `project()`, or pass `-DCMAKE_BUILD_TYPE=Release` from build_core.py for single-config generators. Say which, and why, in the file. A build/ configured before the fix keeps its cached Debug, so build_core.py must detect a cached Debug (or any non-Release type it did not ask for) and either reconfigure or refuse with the value, not build Debug silently.
2. A test that holds it: the cache build_core.py writes says Release (or the multi-config build used Release), seen to fail on today's code.
3. Measure steps/s before and after on one AVR, one Cortex-M0 and one RISC-V board through `session.run`, dated, and correct any figure in the page or docs that the change makes wrong (clock.js's header measures an Uno; check it against the new core rather than assuming).
4. The full suite still passes on the Release core: tests that count steps are unaffected by speed, but a test that times anything is not.

**Note 2026-10-10:** STEPS 1-4 DONE at d661942. The cores build Release on every generator; a tree cached Debug is reconfigured, saying so; nothing failed only in Release.

THE MECHANISM, read in the installed CMake (4.4.2, pip's, under miniconda3/Lib/site-packages/cmake/data/share/cmake-4.4/Modules) and reproduced. Platform/Windows-MSVC.cmake:150 is `set(CMAKE_BUILD_TYPE_INIT Debug)` under "# default to Debug builds"; CMakeInitializeConfigs.cmake:22, called from CMakeCXXInformation.cmake:100 inside project(), does `set(CMAKE_BUILD_TYPE "${CMAKE_BUILD_TYPE_INIT}" CACHE STRING ...)` for a single-config generator. A scratch project printing CMAKE_BUILD_TYPE either side of project() under Ninja read '' before and 'Debug' after; with the default moved before project() its cache said Release. GENERATOR_IS_MULTI_CONFIG is readable before project() (1 for Visual Studio 17 2022 and Ninja Multi-Config, whose caches hold CMAKE_CONFIGURATION_TYPES and no CMAKE_BUILD_TYPE). The CMAKE_BUILD_TYPE environment variable is applied by CMake itself inside project(), so a default before project() would beat it: measured, RelWithDebInfo in the environment became Release until the default yielded to it. With the final CMakeLists.txt it caches RelWithDebInfo, and build_core.configure then reconfigures that tree Release, saying so.

THE FIX. CMakeLists.txt sets the Release default before project(), when the generator is single-config, no type is cached or named, and $CMAKE_BUILD_TYPE is unset; the dead block after project() is gone. Chosen over -DCMAKE_BUILD_TYPE=Release from build_core.py because a default in CMakeLists.txt holds for every configure that names no type -- by hand, an IDE, CI -- and a flag holds for the script alone. What no default reaches is a tree cached Debug before the fix, so build_core.py gains cached_build_type(build_dir) (None for multi-config, "" for an untyped cache) and configure(build_dir, env): configure naming no type, read the cache back, and a single-config tree holding anything but Release is reconfigured with -DCMAKE_BUILD_TYPE=Release and a stderr line naming what it found, then checked again, BuildError with the value if it still is not. Reconfigured rather than refused: build/ is the script's tree and the script builds Release; a Debug build belongs in its own directory. Seen on lane3's own build/: "build_core: ...\build is configured 'Debug', not Release; reconfiguring it Release", then FLAGS /O2 /Ob2 /DNDEBUG -MD where they were /Zi /Ob0 /Od /RTC1 -MDd.

ENSURE_BUILT IS UNCHANGED, on purpose, and its docstring says why. It has never rebuilt an existing library -- not for a source change either: lane3's riscv32.dll predated master's OH-161 ABI and refused to load (no riscv32_map_snapshot_counter) until build_core.py was run. Rebuilding from inside a load would relink DLLs that the server or another session may hold open, and a failed build there reaches a suite as a skip (the cores' conftests turn AbiError into skip). Instead test_this_checkouts_build_is_release FAILS on any build/ that is not Release and names the command, so every checkout configured before this fix -- main, lane2, lane3 and lane4 all cached Debug on 2026-10-09, each its own build/, nothing shared -- fails it until `python tools/build_core.py` is run there once.
