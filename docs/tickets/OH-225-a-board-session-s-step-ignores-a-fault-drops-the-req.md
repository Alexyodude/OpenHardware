Found by OH-223 and its review (2026-10-12), by reading and through a live server. OH-223 gave the i8086 and AVR bindings a `HostFault(AbiError)` for a fault ctypes catches on the host, and made the 8086 debugger's session stop as "faulted". The board side is not done, because its files belong elsewhere:

1. `core/cortexm0/abi.py` and `core/riscv32/abi.py`: `cortexm0_step` and `riscv32_step` are bare foreign calls, so an `OSError` escapes `Cpu.step` and `BoardSession.run`, and `/api/board/run` drops the request. Each wants the AVR treatment from OH-223 (a HostFault naming where the core left the PC, no per-step read), or the instruction-start export OH-223's review recommended for the i8086.
2. `webui/api.py`'s `BoardSession.step` does not check status: after a run stopped on a host fault, `POST /api/board/step` answers 200 and steps the half-executed machine on (seen: the AVR's pc moved to 22).
3. `BoardSession.step` re-raises the core's `AbiError` and `Handler._api` maps none, so `POST /api/board/step` whose step faults gets no reply (RemoteDisconnected). That is true today for `Unimplemented` and `MemoryFault` as well as a host fault.
4. `BoardSession.run` reports a host fault as "stopped", the word a firmware memory fault gets; a distinct "faulted" would let the page say the simulator is at fault, as the 8086 debugger now does.

Claims: `core/riscv32/**` and the borrowed `webui/api.py` are OH-161's (api.py is OH-172's, lent to OH-161); `core/cortexm0/abi.py` and `webui/emulator_server.py` check with `tools/tickets.py owner` when this starts. Borrow rather than overlap.

STEPS: each of the four, with a test seen to fail first using OH-223's technique (monkeypatch the cached CDLL's step to raise OSError on the Nth call) through the real path to the server's answer.

ITEM 1. Each core's ABI Handle records the PC its step began at, one store, before the step: on the Cortex-M0+ that is before both a due SysTick's exception entry and the fetch. cortexm0_step_entry and riscv32_step_entry export it (CORTEXM0_ABI_VERSION 13 -> 14, RISCV32_ABI_VERSION 4 -> 5, in abi.h and abi.py; load() refuses another version). riscv32's handle was the bare riscv32::Cpu, so abi.cc gains the Handle struct the other three cores have. Each abi.py raises HostFault(AbiError) from the OSError with at (where the step began), code (the first two halfwords there: BL is Thumb's one 32-bit encoding, and an RV32 instruction is one or two 16-bit parcels) and left (the PC the core left). Each read back is its own try; "access violation writing" says to restart the process rather than reload; a closed Cpu is refused before the foreign call. Nothing is read per step. Neither binding has a run, and no foreign call but *_step executes instructions.

ITEM 2. BoardSession.step refuses a session that is not running, raising the core's own AbiError naming the status and the detail, and records a stop it raises (status and detail, through _stop, which run uses too) before raising it, so a run that follows takes 0 steps. It still raises: tests/avr/test_arduino_sketch.py and the board-claims evidence count on a step that returns normally meaning an instruction executed.

ITEM 3. /api/board/step calls BoardSession.run instead of step. run reports a stop rather than raising it and refuses a stopped board, so a step that stops (HostFault, Unimplemented, MemoryFault) answers 200 with the state, whose status and detail say why: the code /api/board/run and the 8086's /api/step answer a stop with. count is now a budget like run's steps, so outside 1..MAX_RUN_STEPS it is refused 400 budget-refused, where count 0 used to step nothing and a huge count would have pinned the server. Handler._api still maps no core AbiError; no other route raises one.

ITEM 4 (cf304fd, held). _stop records "faulted" for the core's HostFault and "stopped" for anything else; RunResult's and BoardSession's docstrings and the /api/board/run wire note say so.

COST, measured on this machine, best of 7 runs of 200,000 steps, before (94d57f6) and after (16596b6): Cortex-M0+ Cpu.step 0.206-0.212 us and 0.209-0.213 us; RISC-V Cpu.step 0.238-0.253 us and 0.241-0.255 us; BoardSession.run on the XIAO RP2040's blink 0.243-0.245 and 0.232-0.233 us a step, on the XIAO ESP32-C3's 0.287-0.292 and 0.287-0.293. FOLLOW-UP, the reviewer's open question, not changed here.
