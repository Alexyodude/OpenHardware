# Board intake at catalogue scale — strategy

OH-205, 2026-10-08. Derived with the `feature-strategy` skill. The ledger is
`docs/features/intake.md`; what heypcb.ai did is
`docs/research/heypcb/README.md`.

## 0. What was asked, and the answer

The user asked how heypcb.ai came to list so many open-source boards, and said
the goal is an emulator for all of them.

**heypcb searched one host for one format.** Every public GitHub repository
containing a KiCad project is imported, attributed to its owner's login,
licensed as the repository declares, and filed by the author's own words. That
is 11,030 boards. This repository has 37: twenty-five XIAOs found by Seeed's
naming, the Arduino Uno, and eleven rows a person wrote.

**"An emulator for every board" is not one emulator per board.** It is four
things at four different scales, and only one of them grows with the number of
boards:

| Thing | One per | Exists here | Grows with |
|---|---|---|---|
| CPU core | instruction set | AVR8, Armv6-M, RV32, 8086 (`core/`) | architectures — a handful |
| peripheral set | chip | six chips run (§1.5) | chips — tens |
| part model | part | the nodal solver and the parts on it (OH-79) | parts — hundreds |
| board description | board | 37 (`python tools/inventory.py`) | **boards — thousands** |

The first three are what the core tickets already order. The fourth is the
only one where heypcb's number and this repository's differ by a factor of
three hundred, and it is the one heypcb's method speaks to. So the ledger is
intake: the board description, proposed from the vendor's own files instead of
written.

## 1. Phase 0 — what exists, with evidence

### 1.1 How a board comes in today

- A **source** is a hand-written row of `tools/board_sources.py`: one per
  vendor repository or download, each citing the survey row it came from.
- A **XIAO** is found by its name; the **Arduino Uno** is an `IRREGULAR`
  entry in `webui/boards/catalogue.py`; every other board is a hand-written
  `Row` in `tools/board_manifest.py` `ROWS` — eleven of them at `393d452`.
- A row names: the source, the board file (`cad`), the schematic, the header
  elements (`select`), the chip, the Arduino package and variant, the labels,
  where the licence is stated, a prose reason for each pad that reaches no
  chip pin, and a `PinTable`. `python tools/board_manifest.py --check` reads
  all eleven and writes nothing.

### 1.2 Identification already exists, the other way round

`tools/import_pindefs.py:908` (EAGLE) and `:977` (KiCad) find a board's chip
as **the one placed part whose `(package, value)` equals the row's
`PinTable`'s**, and refuse when it is not exactly one. Given a table, it finds
the part. Intake needs the inverse: given a board, which table.

The readers carry what that needs. `tools/eagle.py` `Board.elements` have a
package, a value and pads with nets; `tools/kicad.py:526` `Placement.value`
is documented as "how `tools/import_pindefs.py` finds a board's chip", beside
the footprint name and pads with nets. KiCad 5 board files do not read yet — OH-198.

### 1.3 Why the key does not scale, measured

The eleven rows use **eleven different `(package, value)` keys for four
chips**, because each vendor spells the same module differently:

| Row | package, as the vendor spelt it | value |
|---|---|---|
| Adafruit Feather ESP32-C6 | `ESP32-PICO-MINI` | `ESP32-C6-MINI_MINI` |
| SparkFun Qwiic Pocket ESP32-C6 | `ESP32-C6-MINI-1` | `ESP32-C6-MINI-1` |
| PCBCUPID Glyph C6 | `ESP32-C6-MINI-1_EXP` | `ESP32-C6-MINI-1-N4` |
| SparkFun Pro Micro ESP32-C3 | `ESP32-C3-MINI-1` | `ESP32-C3_MINI-1` |
| PCBCUPID Glyph C3 | `ESP32-H2-MINI-1_EXP` | `ESP32-C3-MINI-1-N4` |
| Olimex ESP32-C3-DevKit-Lipo | `ESP32-\xadC3-\xadMINI\xad-1` (three soft hyphens, U+00AD) | `ESP32-C3-MINI-1-N4` |

**Two of the eleven place their module on a footprint named for a different
part**: the Feather C6's is named for the ESP32-PICO-MINI, and the Glyph C3's
for the ESP32-H2-MINI-1. A classifier reading footprint names — or, as heypcb
does, the author's title and topics — calls the Glyph C3 an H2.

And the tables are copies. Within each module, the three ESP32-C3-MINI-1
tables, the three ESP32-C6-MINI-1 tables and the two RP2040 tables agree on
`cite`, `url`, `pdf_sha256`, `pins` and `not_gpio` — the datasheet half — and
differ only in the key, in `footprint_pads` — how the vendor's footprint
numbers the exposed pad, `49.1` against `49_1` against not at all — and in
`gpio`, which by its docstring "holds only the pads some row's header
reaches". So the datasheet is read once per module and keyed
once per vendor spelling. Intake has to key it once per datasheet.

### 1.5 What runs

`webui/boards/catalogue.py:190` `FIRMWARE_VERIFIED`: RP2040, SAMD21,
ATmega328P, ESP32-C3, ESP32-C6, ESP32-C5. The rest wait on cores, and the
next cores wait on oracles: Armv8-M (OH-36, blocked), Armv7E-M (OH-64), Xtensa
(OH-38, blocked — "both oracles are the same oracle"), and the capture harness
that would make silicon the oracle for the last two (OH-159).

## 2. The cores the catalogue waits on — a recommendation, not cells

Cores are other tickets' work and are not cells here. Read against heypcb's
filters and the arduino-esp32 count:

| heypcb filter | boards | needs | state |
|---|---|---|---|
| Arduino / AVR | 752 | AVR8 | ATmega328P runs; other AVR parts are this core with other peripherals |
| ESP32 | 647 | RV32 **and Xtensa** | RV32 parts run; 82% of arduino-esp32 boards are Xtensa — OH-38 |
| RP2040 | 374 | Armv6-M | runs |
| STM32 | 358 | Armv6-M (C0/G0/F0/L0), Armv7-M (F1) and Armv7E-M (F4/L4/G4…) | M0+ families can reuse `core/cortexm0`; Armv7E-M is OH-64; Armv7-M has no ticket. The split between them is not established |
| ESP8266 | 169 | Xtensa LX106 | OH-38's oracle problem, again |
| nRF52 | 100 | Armv7E-M | OH-64 |
| Teensy, SAMD51 | 43, part of 27 | Armv7E-M | OH-64 |
| Raspberry Pi | 268 | a Linux computer | out of scope — these are hats and carriers |
| FPGA | 187 | gateware | out of scope — no CPU to emulate |

**The two largest blocked families, Xtensa and Armv7E-M, are blocked on the
same thing: an oracle.** OH-159 — the hardware capture harness, "so silicon is
the oracle Xtensa and Armv7E-M lack" — is the one ticket that unblocks both,
and it is P2. That is the strongest recommendation this survey produces, and it
is for whoever holds OH-159, OH-38 and OH-64 to act on; this ticket does not
edit theirs.

## 3. Phase 1 — the matrix

Stage × input. The stages are the fields of a row; the inputs are the formats
the eleven rows were written against.

| | EAGLE `.brd`/`.sch` (6 rows) | KiCad 6+ `.kicad_pcb` (5 rows) | KiCad 5 | Altium, OrCAD |
|---|---|---|---|---|
| find the board file | cell | cell | OH-198 | no reader |
| identify the chip | cell | cell | OH-198 | no reader |
| join the variant | cell | cell | — | — |
| select the headers | cell | cell | — | — |
| find the licence | cell | cell | — | — |
| reason an unreached pad | cell | cell | — | — |

Every `cell` above is one ledger row covering both formats: the readers in
`tools/eagle.py` and `tools/kicad.py` already present both as parts with pads
on nets, so the stage does not split by format. Altium and OrCAD — Nordic,
WCH, most of M5Stack, the Pico — have no reader and are not cells. KiCad 5 is
OH-198's.

## 4. Phase 2 — tier

All `F0`. A board description has no timing and no electrical behaviour; the
tier scale does not apply, as `docs/features/webui.md` already says of a user
interface.

## 5. Phase 3 — oracles

**The eleven manifest rows are the answer key.** Each was written by hand
against the vendor's files, so a proposal that reproduces them reproduces that
reading, and a proposal that differs points at a field where one of the two is
wrong. Which one is settled by opening the vendor's file. That is weaker than
silicon and stronger than "it looked right". It is the feature-strategy
skill's regression oracle — there "a previously captured VCD" — carried from a
waveform to a row, with the vendor's file as the tie-break.

**`boards.txt` is the independent one.** A variant's `build.mcu` or
`build.chip` is written by the people who maintain the Arduino package, not by
the people who drew the board. `intake.chip.agrees-with-variant` holds the
identified chip to it, and the two can disagree.

**The datasheet confirms identity by pins, not by name.** A part is the chip
only if every pad the datasheet calls ground lands on one net and every supply
pad on one net. The value proposes and the pins confirm, because neither is
enough alone: the Glyph C3's value says C3 on a footprint named for the
ESP32-H2-MINI-1, and whether the two modules' ground and supply pads are
numbered alike — which would leave the pins unable to tell them apart — is not
established.
That PCBCUPID could reuse the footprint suggests they may be.

**Two cells have no oracle and stay `planned`**: the host search, because
nothing says what it should have found, and the histogram, which is only as
true as the identification under it.

## 6. Phase 4 — slices

Each slice is its own ticket, and each ends in something shown.

**S1 — the chip, from the board file alone.** `intake.chip.by-value`,
`.module-to-soc`, `.supply-pins-confirm`. Demo:
`python tools/propose_board.py --check` prints one line per manifest row,
`match` or the field that differs; eleven `match`.

**S2 — the rest of the row.** `intake.find.*`, `.variant.join`,
`.headers.select`, `.licence.statement`, `.chip.agrees-with-variant`, ending
in `intake.row.whole`. Demo: the same command compares whole rows; eleven
equal field for field, or each difference resolved against the vendor's file
and recorded.

**S3 — the prose.** `intake.reasons.unreached-pad`: for a pad that reaches no
chip pin, a generated reason naming the net and the part it does reach. Demo:
the nine hand-written reasons reproduced by net and part.

**S4 — a board nobody wrote a row for.** A public repository on a chip that
runs, with a variant in an already-fetched package, proposed by S1–S3, written
by `tools/board_manifest.py`, composed by `tools/compose_board_3d.py`. Demo:
a thirty-eighth board whose row was proposed, not written. Candidates are the
107 RP2040 and 60 running-RV32 variants in §1.4 whose vendors publish a board
file; which ones do is not established.

**S5 — the host.** `intake.fetch.sparse`, `.licence.refuse-undeclared`,
`.search.host`, `.demand.chip-histogram`: search GitHub for public `.kicad_pcb`
files as heypcb does, fetch only the board file, its schematic and its licence
into `third_party/`, refuse a row where no licence is declared, and count
boards per identified chip. Demo: the histogram beside heypcb's filters —
chips read from netlists against chips read from titles — and the order of
§2 recomputed from it rather than argued.

## 7. The long tail needs a rule this repository does not have yet

OH-174's layer 3 is reached through a vendor's board-support package — pins
"read from a vendor's board-support package" — and layer 4 is the chip's
`FIRMWARE_VERIFIED` entry, which a manifest row never inherits: its own claim,
under `rules/board-claims.md` §7 and §11, needs an image built against **the
board's own variant**.
That is right for the eleven rows and it is a wall for the tail. Almost none of
heypcb's 11,030 are a vendor's board with an Arduino variant; they are
someone's keyboard, someone's synth, someone's robot controller, built around a
chip that runs here.

For those, the netlist already says which chip pin each header pad reaches
(OH-178 reads it that way for the rows), and the chip's own generic variant can
build the image. Whether that is enough to say a board runs is a
`rules/board-claims.md` decision, and it should be made before S5, because S5's
histogram counts boards that S1–S3 can describe and that rule cannot yet
promote. Recorded here; not decided here.

## 8. Proposed shape of S1 — to be confirmed before any body is written

Per `.claude/CLAUDE.md` rule 2, as code and not prose.

```
tools/propose_board.py              new -- a board's chip, proposed from its own board file
tests/rules/test_propose_board.py   new -- the eleven manifest rows as the answer key
```

Neither path is claimed by any open ticket (`python tools/tickets.py owner`).
`tools/board_manifest.py` and `tools/import_pindefs.py` are read, not changed.

```python
@dataclasses.dataclass(frozen=True)
class Datasheet:
    """One module or chip, keyed by its datasheet rather than any vendor's spelling."""
    soc: str                          # "ESP32-C3" -- a key of webui.boards.catalogue.CHIPS
    stem: str                         # "ESP32-C3-MINI" -- the datasheet's own product name
    table: board_manifest.PinTable    # one of the group; their datasheet half is identical (§1.3)

@dataclasses.dataclass(frozen=True)
class Placed:
    reference: str                    # "U1"
    package: str                      # as the vendor spelt it
    value: str                        # as the vendor spelt it
    pads: tuple[tuple[str, str | None], ...]   # (pad, net)

@dataclasses.dataclass(frozen=True)
class Identified:
    placed: Placed
    datasheet: Datasheet
    confirmed_by: tuple[str, ...]     # "U1.49 GND", "U1.3 3V3" -- the pads that proved it

def placed_parts(path: pathlib.Path) -> tuple[Placed, ...]:
    """Every part on one EAGLE `.brd` or KiCad `.kicad_pcb`, by extension."""

def normalise(spelling: str) -> str:
    """'ESP32-\\xadC3_MINI-1' -> 'esp32-c3-mini-1': soft hyphens out, `_` read as `-`, case-folded."""

def identify(parts: Sequence[Placed], datasheets: Sequence[Datasheet]) -> Identified:
    """The one part whose value starts with a datasheet's stem and whose ground and
    supply pads land where that datasheet says. Raises naming every candidate and
    why each failed, when there is not exactly one."""

def check(rows: Sequence[board_manifest.Row]) -> int:
    """Each row's chip, proposed from its board file alone; prints `match` or what
    differs. 0 all match, 1 any differs, 3 a source not fetched -- and says SKIPPED."""
```

```
python tools/propose_board.py --check
  check(board_manifest.ROWS)
    for row in rows:
      parts = placed_parts(<fetched source>/row.cad)   eagle.read_board | kicad.read_board
      found = identify(parts, DATASHEETS)             DATASHEETS: one per datasheet, six today
      compare found.datasheet.soc with row.chip
      compare found.placed with the one part row.pin_table's key selects
```

`DATASHEETS` is built from the existing `PinTable`s grouped by `(url,
pdf_sha256)` plus one stem per group — six today (ESP32-C3 chip, ESP32-C3-MINI,
ESP32-C6-MINI, ESP32-C6-WROOM, ESP32-C5-WROOM, RP2040) against eleven keys.

### Least confident

1. **Matching the value by normalised prefix.** The Feather C6's value is
   `ESP32-C6-MINI_MINI`, so the stem has to stop at `ESP32-C6-MINI`, and a stem
   that short also prefixes values it should not. Longest stem wins, and the
   pins decide between pin-compatible modules — but a tail board whose value is
   `~` or a reference defeats the value entirely, and the fallback, every
   datasheet tried against every part with enough pads, has nothing to prefer
   between the C3-MINI-1 and the H2-MINI-1.
2. **Grouping the `PinTable`s rather than merging them.** S1 reads
   `tools/board_manifest.py` without changing it. If someone merges the copies
   into one table per module, the grouping becomes a lookup; until three of
   them change together for one reason, `.claude/CLAUDE.md` rule 7 says leave
   them.
3. **Confirming by net identity, not net name.** All ground pads on one net is
   what the datasheet states; `GND` is the vendor's word. A board that joins
   analogue and digital ground through a net-tie would fail it honestly and
   need a reason.
4. **Whether eleven careful vendor boards are a fair key for the tail.** All
   eleven are vendor boards with a variant; six are EAGLE. S1 passing shows the
   method reproduces careful work. Whether it survives hobbyist KiCad is
   measured only in S5, which has no oracle.

## 9. What this does not do

- Write any code. OH-205 is the research, the ledger and this plan.
- Copy anything heypcb copies. Fetching stays in the git-ignored
  `third_party/`; nothing fetched is committed.
- Edit another ticket. The core order in §2 and the rule question in §7 are for
  OH-159, OH-38, OH-64 and `rules/board-claims.md`'s owners.
- Cover FPGA boards (187) or Raspberry Pi hats (268): neither has a
  microcontroller this project emulates.
