# Strategy — web UI

**Date:** 2026-08-10
**Ledger:** `docs/features/webui.md` (43 cells)
**Status:** derived, not started
**Derived by:** the `feature-strategy` skill

This slice was originally last on the roadmap. It is now first, and the reason
is not preference — it is that the evidence behind its original placement was
wrong. This document records both the correction and the new order.

## 1. The correction that moved this slice

An earlier reading of `src/lib/rcontrol.cc` extracted its command vocabulary
with a regex over bare quoted tokens. That regex **missed every command matched
with `strncmp` and a trailing space**, which is most of the interesting ones. On
that incomplete evidence this document's predecessor concluded the remote
interface was largely read-only and that a UI would need substantial new C++.

Enumerated properly, by reading the dispatch branches rather than pattern-
matching strings, the surface is:

**`set`** — four branches at `src/lib/rcontrol.cc:1127`:

| form | reaches |
|---|---|
| `set board.in[NN] = v` | board inputs: buttons, pots, jumpers; also raises `Input->update` |
| `set apin[NN] = f` | `SpareParts.SetAPin` or `Board->MSetAPin` |
| `set pin[NN] = v` | `SpareParts.SetPin` or `Board->MSetPin`, under `IoLockAccess()` |
| `set part[N].in[M] = v` | a specific spare part's input |

**`get`** — eight branches at `src/lib/rcontrol.cc:724`: `board.in[]`,
`board.out[]`, `apin[]`, `pin[]`, `pinl[]`, `pinm[]`, `part[N].in[M]`,
`part[N].out[M]`.

Plus `spadd` / `spdel` to place and remove parts at runtime, `sprdcfg` /
`spwrcfg` to configure them, `loadhex` to load firmware, `sim` / `reset` /
`start` / `stop` for run control, and the `osc*` family for the scope.

**That is the entire Wokwi interaction model, already implemented.** Press a
button, turn a potentiometer, drag a part onto the board, delete it, wire a pin,
read an LED, load a hex file, scrub a scope — every one has a command already,
already exercised by upstream's own `tests/python/test_blink.py`.

**Consequence: the web UI requires no new C++ at all.** It is a bridge plus a
front-end. Of every slice on the roadmap it is the only one that delivers
something visible using engines that already work — `simavr` and `picsim` are
built and tested today. The 8086 core, by contrast, delivers nothing anyone can
see until it is nearly complete.

The lesson is the one this project keeps relearning, recorded in the skill's own
red flags: a regex over source is a directory listing wearing a costume. Read
the dispatch.

## 2. The other correction: the WASM build is not reproducible

`src/Makefile.JS` compiles with Emscripten and `-s USE_SDL=2`, linking
`liblxrad_SDL2_js.a`, and emits `picsimlab_wasm.html`. It is real, and an online
build of PICSimLab exists. But it cannot be reproduced from this repository:

- **No build script.** Every other target has one under `bscripts/`. There is no
  `build_js.sh`.
- **No CI.** No workflow references `emcc`, `emscripten`, `wasm`, or
  `Makefile.JS`.
- **`template.html` is absent** from the tree, yet `--shell-file template.html`
  is required to link.
- **`src/assets` is absent**, yet `--preload-file assets` is required.
- **Hardcoded sibling checkouts:** `../../LXRAD_SDL2/`, `../../picsim/`,
  `../../ucsim-0.6/`, `../../simavr/`. It even links
  `../../LXRAD_SDL2/teste/zlib-master/contrib/minizip/minizip.a` — a zlib
  checkout inside another project's *test* directory. `Makefile.JSMT` similarly
  wants `../teste/glib_js/target/`.

That is a maintainer's personal working layout, not a build system. Treating it
as a working foundation — which the earlier roadmap did, calling this slice a
"new front-end over the NOGUI/JS core" — was unjustified.

Also note the JS build links only `libpicsim_js.a` and `libsimavr.a`. **There is
no QEMU in the browser build**, so ESP32 and STM32 are unavailable there. "Run
everything in a browser" is not currently on offer at any price.

## 3. The decision: one UI, two transports

The requirement is local-first and open source, with hosting optional and
paid — never required. Both transports satisfy that; they differ in install
story, not in whether anyone must rent a server.

```
        browser front-end  (HTML/DOM)
                 |
          one API adapter          <- the only thing either transport sees
           /            \
   websocket             ccall
       |                   |
  bridge process      WASM module
       |                   |
  picsimlab_NOGUI     everything in-page
  (scripted build)    (build to be reconstructed)
```

**Transport A — local process.** A bridge on `localhost` speaking rcontrol's TCP
protocol to a headless `picsimlab_NOGUI`. Reproducible today: the NOGUI build is
scripted at `bscripts/build_package_NOGUI.sh`, and the protocol is already used
by upstream's tests. Runs offline, no account, no network. Install a binary,
open a page.

**Transport B — WASM.** Everything in the page, zero install, one file. This is
the end state and the closest thing to Wokwi's deployment. It is gated on
reconstructing the build described in §2.

**Choosing A does not forfeit B.** Both speak the same rcontrol-shaped API, so
moving in-browser is a swap behind the adapter, not a UI rewrite. The
`EXPORTED_FUNCTIONS` list in `Makefile.JS` currently exposes seven symbols —
`_main`, `_file_ready`, `_lxrad_scale_up`, `_lxrad_scale_down`, `_dirt_load`,
`_SimRun`, `_SimStat` — nowhere near enough. Cell `webui.wasm.export-api`
exists to widen it to the same surface the bridge already uses, which is why
the API is worth pinning down first regardless of which transport ships first.

Hosting, if it is ever offered, is the same bridge with a different URL. That
is the whole of the paid story: local is the default and the free path, remote
is a deployment detail.

## 4. The oracle question, which is unusual for a UI

Interfaces are normally where verification degenerates into "it looked right".
Here it does not, because **the simulator is the oracle for the UI**.

Every interaction has a readable consequence. Pressing a button in the browser
is correct only if `get part[N].in[M]` subsequently reports the new value.
Rendering an LED is correct only if it matches `get part[N].out[M]`. Placing a
part is correct only if it appears in `splist`. The UI never grades its own
homework, and no cell is satisfied by a screenshot.

API cells use a **differential** oracle instead: the same command through the
bridge must return exactly what a direct TCP session returns. That makes the
bridge's correctness a property anyone can check without a browser at all.

Two oracles are weaker and are marked as such by what they can prove:
`pzw` round-tripping covers workspace load and save, and `network-log` covers
only the offline guarantee — it proves no request was made, not that the page
is correct.

`F1` through `F3` are not used anywhere in this ledger. Those tiers describe
timing and electrical fidelity, which a user interface does not possess. Every
cell is `F0`. That is a limit of the tier scale, not a statement of low ambition,
and it is recorded here so nobody later reads forty `F0` rows as timidity.

## 5. Slice order

**5a — bridge, headless.** `webui.bridge.*` plus `webui.api.*`. No browser at
all: the deliverable is a bridge with a differential test suite proving each
command matches a direct TCP session. Demo: a scripted session drives a real
simulation and asserts pin states. This is the slice that must not be skipped —
it is where correctness is established while it is still cheap.

**5b — minimum visible loop.** `board-canvas`, `run-controls`,
`firmware-picker`, `led-render`, `button-press`. Demo: load blink, press run,
watch an LED blink in a browser, press a button and see the simulation respond.
The first moment this project looks like the thing it set out to be.

**5c — parts.** `part-palette`, `part-place`, `part-remove`, `part-config`,
`pot-drag`, `display-render`, `pin-inspector`. Demo: build a circuit in the
browser without touching a file.

**5d — instruments and workspaces.** `scope-view`, `serial-terminal`,
`ws.load-pzw`, `ws.save-pzw`, `ws.round-trip`. Demo: save a workspace, reopen
it, get the same circuit.

**5e — packaging.** `pkg.one-command-local`, `pkg.offline-guarantee`. Demo: one
command, no network, works on a disconnected laptop.

**5f — WASM.** The `webui.wasm.*` cells, ending at `single-file`. Demo: open one
`.html` with no install and no process. Last because it is gated on
reconstructing a build nobody has reproduced, and because everything above ships
without it.

## 6. Roadmap change

Previous order: 8086 core, analog solver, mixed-signal bridge, web UI.

New order: **web UI, 8086 core, analog solver, mixed-signal bridge.**

The justification is §1: the UI is the only slice that produces something
visible using engines that already work, and it needs no new simulator code. The
prior placement rested on the incorrect belief that rcontrol could not drive a
UI and that a working JS core existed. Both were wrong, in opposite directions —
the interface was richer than believed, and the build was poorer.

## 7. What this slice is not

- Not a rewrite of the lxrad desktop UI, which stays exactly as upstream ships
  it and remains the supported native path.
- Not an ESP32 or STM32 story in the browser: the JS build has no QEMU (§2).
- Not a hosted service. Hosting is an optional deployment of the same bridge,
  and the local path never requires it.
- Not blocked on the 8086 core or the analog solver. It runs on `simavr` and
  `picsim` as they exist today.
