## 2. Root-cause narratives

### 2.1 The 8088 clears AF on logical operations — the manual is wrong

**Symptom.** First full corpus run: 430,041/490,000 (87.76%). Every 100% file was
arithmetic or control flow; **every failing file was a logical op** (OR `08-0B`,
AND `20-23`, XOR `30-33`), all stuck near exactly 50%:

```
48.7%  20.json    4870/10000
49.6%  08.json    4957/10000
50.5%  30.json    5050/10000
...
or cl, bl [2] (0A CB): register flags: expected 0000, got 0010
```

Every divergence was `0x10` — the AF bit, and always *we* had it set where
hardware had it clear.

**Wrong hypothesis, ruled out immediately.** "The logical result is wrong." It is
not: no case ever disagreed on the destination register or on memory, only on
flags. Checking `changed_registers` on failing cases showed the value operand
matched every time.

**Root cause.** `core/i8086/alu.cc` cleared CF and OF for the logical
operations, per the Intel manual, and left AF alone because the manual calls it
**undefined**. Taking "undefined" to mean "unchanged" is the bug.

**Evidence — measured, not inferred.** Asked the corpus directly:

```
08: AF set BEFORE in 5043/10000,  AF set AFTER in 0/10000
09: AF set BEFORE in 4935/10000,  AF set AFTER in 0/10000
20: AF set BEFORE in 5130/10000,  AF set AFTER in 0/10000
21: AF set BEFORE in 5059/10000,  AF set AFTER in 0/10000
30: AF set BEFORE in 4950/10000,  AF set AFTER in 0/10000
31: AF set BEFORE in 5016/10000,  AF set AFTER in 0/10000
```

Set beforehand roughly half the time. Set afterwards in **0 of 60,000**. The
part clears it unconditionally.

**Fix.** `core/i8086/alu.cc`, the `kOr/kAnd/kXor` arm:

```cpp
SetFlag(flags, kCarry, false);
SetFlag(flags, kOverflow, false);
SetFlag(flags, kAuxCarry, false);   // <- this line
```

Result: 490,000/490,000.

**Generalization.** *"Undefined" in a vendor manual is a statement about what
the vendor will promise, not about what the silicon does.* Where a hardware
oracle exists, it outranks the document. Note also the shape of the failure:
**~50% is the signature of a single boolean flag being carried instead of
set** — it passes exactly the half of cases where the stale value happened to
be correct. A rate near 50% on an otherwise-working opcode should send you
looking for one bit, not for the arithmetic.

### 2.2 The prefix guard read a prefix as an opcode

**Symptom.** Found while probing adversarially, not by a failing test:

```
 6 prefixes -> opcode 90 len  7   valid
 7 prefixes -> opcode 2E len  7   <- wrong opcode, wrong length
```

**Root cause.** `decode.cc` capped the prefix scan at `at >= 6`, then `break`,
then read the next byte as the opcode — but that byte is another prefix. It
produced a **silently wrong instruction** rather than refusing one.

**Fix.** `kMaxLength = 15` (the limit later x86 parts adopted), and exceeding it
sets `Instruction::valid = false`, which `Step` refuses. Verified: 14 prefixes
decode, 15+ refuse with IP unchanged.

**Generalization.** A bound that exists to stop an infinite loop must **fail**,
not **stop and carry on**. Stopping and continuing converts a hang into
corruption, which is worse because it is quiet.

### 2.3 Word access wrapped at the megabyte instead of the segment

**Symptom.** None — no test failed. Raised by architect review and reproduced
deliberately:

```
read_word(1000:FFFF) = 77EF     (physical+1, the next paragraph)
hardware wants        BEEF      (high byte from 1000:0000, same segment)
```

**Root cause.** `Cpu::ReadWord`/`WriteWord` took a **physical** address and
added 1. On real hardware a word access wraps the **offset** inside the segment.

**Fix.** Added `ReadWordAt(segment, offset)` / `WriteWordAt(...)`; the physical
form is retained and documented as an inspection accessor operands must not
use. `Push`/`Pop` use the segment-aware pair — this was latent until PUSH/POP
landed in the same session, where it would have corrupted any stack with
SP near 0xFFFF.

**Generalization.** Two addressing models that agree on the common case and
differ only at a boundary. The API must make the distinction impossible to get
wrong, because a test suite that never lands on the boundary will not find it.

### 2.4 A false claim guarded by a test that could not fail

**Symptom.** Raised by architect review. Three docstrings claimed the register
struct's field order matched the SST8088 corpus. It does not:

```
ours    ax bx cx dx si di bp sp cs ds es ss ip flags
corpus  ax bx cx dx cs ss ds es sp bp si di ip flags
```

The test asserting it compared **sets**, which cannot see order.

**Root cause.** The claim was never load-bearing — every crossing is by name
(`set_regs(**case.initial_regs)`), never positional — so nothing broke and
nothing noticed.

**Fix.** Claim removed from all three files. `test_the_orders_differ_which_is_fine_and_deliberate`
now pins the fact, so nobody re-asserts it.

**Generalization.** A test whose assertion is weaker than its name is worse than
no test: it advertises a guarantee it does not provide. Grep for
`set(...) == set(...)` under any name containing "order".

### 2.5 MSVC needs an environment its installer will not set

**Symptom.** `cl.exe` on PATH, but:

```
LINK : fatal error LNK1104: cannot open file 'kernel32.lib'
```

Adding the Windows SDK to PATH fixed `rc.exe` and produced a near-identical
error two lines later.

**Root cause.** MSVC needs `PATH`, `INCLUDE`, `LIB` and `LIBPATH`, set by
`vcvarsall.bat` and deliberately not global.

**Fix.** `tools/build_core.py` runs `vcvarsall.bat` and captures its
environment — **through a temporary batch file**, because
`cmd /c "call \"path with spaces\" && set"` mangles the quoting into the
command name itself.

**Generalization.** "The compiler is broken" is almost never true; "the
environment is incomplete" almost always is. And `cmd` quoting is not shell
quoting — write a batch file rather than fighting it.

## 3. Reproduce the result, cold

```bash
cd Code/Github/OpenHardware

# 1. Build the core. First run captures the MSVC env; ~10 s.
python tools/build_core.py
#    -> .../build/lib/i8086.dll   95232 bytes   [Linux: libi8086.so]

# 2. The suite.
python -m pytest -q
#    -> 431 passed, 17 skipped     (~8 s on a fresh clone)
#    -> 432 passed, 17 skipped     (~65 s once the corpus is present -- the
#       extra test is the 490,000-case corpus run, and it is the 57 s)

# 3. Every checker.
for c in check_layering check_board_contract check_part_schemas \
         check_licenses check_deltas check_banned_symbols check_ticket_claims; do
  python -m tools.$c
done
#    -> all "OK". check_licenses says 90 files; check_banned_symbols says 10 C/C++ files.

# 4. The hardware check. Corpus is git-ignored; fetch what you need.
bash tools/get_8088_tests.sh --opcodes 00 09 21 29 31 39 50 58 74 8B
python tests/i8086/conformance.py third_party/sst8088/v2
#    -> core: core/i8086
#       100000/100000 (100.00%) across 10 opcode file(s)

# 5. Prove the harness is not the thing passing.
python tests/i8086/conformance.py third_party/sst8088/v2 --baseline --failures 0
#    -> core: none (do-nothing baseline)
#       0/100000 (0.00%)
```

If step 5 reports anything but 0%, the harness has stopped discriminating and
step 4's number means nothing.

**Requires the reference checkout** (`../picsimlab-reference`): `check_layering`,
`check_board_contract`, `check_part_schemas`. Without it they exit **3** and
print `SKIPPED` — that is not a pass. Re-create with:

```bash
git clone https://github.com/lcgamboa/picsimlab ../picsimlab-reference
```

## 5. Open work

1. **OH-4 — shift/rotate, muldiv, string, rep, bcd, io.** *(software-only)*
   **Start here.** Add entries to `Lookup()` in `core/i8086/decode.cc` and cases
   in `Step()` in `core/i8086/exec_core.cc`, then:
   ```bash
   bash tools/get_8088_tests.sh --opcodes D0 D1 D2 D3 F6 F7 A4 A5 AA AB
   python tools/build_core.py && python tests/i8086/conformance.py third_party/sst8088/v2
   ```
   Expect a rate near 0% for each new opcode until its handler is right, then
   100%. **Anything stuck near 50% is one flag bit** — see §2.1.
   Shifts are the known-hard case: the 8086 masks the count differently from
   later parts, and OF is only defined for a count of 1.

2. **The immediate ALU forms are deliberately unimplemented.** *(software-only)*
   `04 05 0C 0D 14 15 1C 1D 24 25 2C 2D 34 35 3C 3D` — `ALU AL,imm8` and
   `ALU AX,imm16`. They take an immediate rather than a modrm, so they decode
   at a different length and are refused rather than misdecoded. `Form::kImm8`
   / `kImm16` need adding to `decode.h` alongside the existing `kRel8`/`kRel16`,
   which are the same shape.

3. **OH-5 — interrupts.** *(software-only)* Depends on stack and control flow,
   both of which now exist. Vector table, `INT n`, divide error, single step.

4. **OH-7 — the emulator UI.** *(software-only)* The application surface the
   user originally asked for: registers, flags, memory, disassembly, step/run.
   `cpu.decode()` already returns everything a disassembly view needs.

5. **OH-10 — PlatformIO / Arduino firmware loading.** *(software-only for the
   parse; blocked for execution)* Only XIAO ESP32-C3 has a backend, inherited
   from PICSimLab's shipped `ESP32-C3-DevKitC-02` on `bsim_qemu`.

6. **OH-9 — PICSimLab adapter.** **BLOCKED: requires a working PICSimLab
   build.** `docs/known-issues.md` 4a.6 — the NOGUI build cannot link on
   Ubuntu 22.04 / GCC 11.4 (`lto1: internal compiler error`), and dropping
   `-flto` does not help because the dependency archives carry LTO IR. The WX
   GUI build reportedly works. Nothing in slices 1–5 above needs this.

7. **`i8086.int.arch-enum` is the one in-progress ledger cell.** The patch
   exists and applies; the cell stays in-progress because the enum change has
   never been compiled into a real PICSimLab. Blocked on the same build as (6).

## 7. Known limitations, and things not worth your time

- **`11/11` on the committed fixtures means almost nothing now.** It is three
  opcodes. The number that matters is the corpus run in §3 step 4. The eleven
  fixtures exist so the suite has *something* offline.
- **CI fetches only ten opcode files** (~14 MB, 90,000 cases), not all 49. A
  green CI is real hardware verification but not exhaustive; run the full
  fetched set locally before claiming an opcode family is done.
- **The corpus test takes 49 s** over 49 files. It skips when `third_party/`
  is absent, which is the default state of a fresh clone.
- **Upstream is unpinned by choice** (`rules/upstream-sync.md` §4). The
  board-contract count moved 42 → 44 during this session because upstream
  added `GetSimBackends()` and `GetDebuggers()`. Expect
  `test_the_real_contract_is_the_expected_size` to fail again when upstream
  moves; update `CONTRACT_SIZE` with the date and revision.
- **Do not add `@pytest.mark.parametrize`.** `tools/inventory.py` counts
  `def test_*` with `ast`, and `test_ast_count_matches_pytest_collection` fails
  on the divergence. Use a loop inside one test. Note this contradicts
  `.claude/rules/tests.md` from the installed template; the repo's own
  constraint wins.
- **The ticket guard is opt-in per clone.** `.claude/` is git-ignored, so the
  `PreToolUse` registration cannot ship. `docs/tickets/README.md` has the
  snippet. `rules/ticket-claims.md` §7 records this honestly.
- **`gh repo view Alexyodude/OpenHardware` still redirects from the old fork
  name.** The fork was renamed to `OpenHardware-fork` and retains both its
  branches; delete it whenever you are satisfied nothing is missing.
- **`LICENSE` says "the OpenHardware authors."** Substitute a legal name if
  the copyright should be attributable.
