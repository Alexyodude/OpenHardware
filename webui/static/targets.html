The one thing that decides the rest §2

A core is only as good as the thing you check it against. The 8086 core reached 2,797,000 hardware-captured cases at 100% because SingleStepTests had already captured them. For every chip below, that corpus does not exist.

And “SST-shaped” does not mean hardware-captured. Only the x86 family (8086/8088/80186/80286/80386/V20) claims hardware generation. ARM7TDMI comes from NanoBoyAdvance, m68000 from MAME, sh4 from Reicast — simulator-generated, like the corpus we would be making. That assumption was load-bearing, and it was wrong.

STM32 — Cortex-M0 / M0+ the build-our-own candidate

FamilyCoreVerdictEvidenceWhat is actually known
C0Cortex-M0+ · 48 MHz BUILD OURS HAL SOURCE Reference chip, on a ~£12 Nucleo-C031C6. It has no PLL — HSI48 plus a divider — so the survey’s four boot spins (a G0 figure) are really three here: HSIRDY, ACR.LATENCY, and SWS == SW.
G0 · L0 · U0Cortex-M0+ BUILD OURS HAL SOURCE Same core, same approach. G0 is where the original four-spin measurement came from.
F0Cortex-M0 (not M0+) DROPPED CMSIS HEADERS No VTOR, and no CONTROL.nPRIV. The vector table is pinned at zero, so a per-case HardFault handler cannot be relocated — which makes the whole fault-outcome design impossible. Two architectural deltas, not one.

The throughput question is answered, and without hardware. Roughly 250–350 cases/sec for a competent rig — a full corpus in 2–3 hours, not two days. The feared 10× spread is host tooling, not physics: pyOCD driving the on-board ST-LINK manages 19/s (42 hours), while OpenOCD in dap-direct mode, or a ~£12 Raspberry Pi Debug Probe, reaches 245–2,000/s. The board decision is really a probe decision.

And the reason to buy silicon changed. Every free Armv6-M model fails to model faults at all: rp2040js never calls exceptionEntry(EXC_HARDFAULT), and thumbulator’s decode_error() prints to stderr and exits. They are a good oracle for the defined instruction space and a null oracle for the fault space — which is where a conformance corpus earns its keep.

Boards carried in the repository python tools/inventory.py

26 board definitions, of which one is wired to the simulator. 582 pads in total; 28 carry a simulator pin index, and all 28 are on Arduino Uno. The 25 Seeed XIAO boards draw to scale and deliberately refuse connections — a pad with a null pin would otherwise wire the circuit wrongly and report success.

Those counts are computed by the generator, never written down. Four tests fail if the README’s list drifts from webui/boards/, and each was verified to fail on real drift before being trusted.

Open — and needing a human

  • Arm FVP licence. Freely downloadable, runs here, models both M0 and M0+. But its supplementary terms prevail over the EULA and scope “Software Models” to Arm architecture licensees. An Armv6-M core here is one. Default: build nothing on it.
  • The Nucleo’s ST-LINK revision. Decides 245 vs 2,000 cases/sec. Answerable from the board’s silkscreen; st.com is unreachable from this network.
  • The UDB toolchain image. Trusim cannot build here — ./do dies at unsupported OS: MINGW64_NT before Ruby or GMP matter. Docker is the only route, and the image denies anonymous pull.
  • What an oracle must prove. The handoff asked whether rvcpp builds and exposes the right shape. Both true. The question nobody specified was does it model what the hardware refuses? — and it does not. That belongs in the acceptance criteria for every candidate oracle, not just this one.
